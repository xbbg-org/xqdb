## Fixed — large q results no longer fail

A legitimate q response is no longer refused for being large. 0.1.4 applied a
hardcoded 512 MiB ceiling to every IPC message, so an ordinary query could fail
with:

```
Decompressed IPC message length 706440911 exceeds the 536870912-byte safety limit
```

The same constant also capped q binary table reads and Kxzip decompression at
512 MiB. All of these ceilings are gone. A result is now bounded only by
available memory and by the q header's own 40-bit length field, and a result
that does not fit returns an error rather than terminating the host process.

Verified against kdb+ over IPC: an 800,000,014-byte frame, and the same value as
a q-compressed frame declaring 800,000,028 decompressed bytes, both of which
0.1.4 rejected.

**What replaced the ceilings.** Bounds that remain are either the wire format's
own or proportional to bytes actually received, so nothing legitimate is refused:

- A declared length reserves at most 32 MiB up front. Beyond that the response
  buffer grows eightfold only once the peer has filled the previous reservation,
  so committed memory stays within eight times the bytes actually delivered.
- A compressed response is rejected when its declared decompressed size is
  unreachable from the bytes received. The q IPC decompressor emits at most 2056
  bytes per 17 input bytes, so 121x is a strict bound; this client's own
  compressor reaches 120.935x on maximally compressible input.
- A Kxzip file is rejected when its declared output exceeds what its own LZ4
  blocks can hold, taken per block as the smaller of the block's uncompressed
  size and 255x its actual compressed bytes. The previous block-count product
  was no real bound: eight bytes of footer metadata bought 4 MiB of permitted
  claim, so an 8 KiB crafted file could demand a multi-gigabyte allocation.

## Fixed — outgoing messages above 4 GiB were framed incorrectly

The request encoder hardcoded the q header's length-extension byte to zero and
wrote a 32-bit length, so a message above 4 GiB declared its length modulo 2^32
and desynchronized the peer. Both the connector and `serializeAsIpcBytes6` /
`serialize_as_ipc_msg6` now write the 40-bit form, bounded by the format's own
maximum of 1,099,511,627,775 bytes.

## Fixed — compressed frames above 4 GiB were unparseable

When a message exceeded 4 GiB the compressor selected compression mode 2 but
wrote the eight-byte decompressed-length prefix at the wrong offset, emitting a
frame no q peer could decode. This path was unreachable while the 512 MiB
ceiling existed and became reachable once it was removed.

## Fixed — a result too large for the machine aborted the process

Allocations sized from wire data went through Rust's aborting allocator, so a
payload larger than available memory killed the host process — the Node worker
or the Python interpreter — with no catchable error. Every process-sized
allocation on the receive path is now fallible and reports an error instead:
message body, decompression target, symbol offsets and values, char-column
views, nested-list payloads and offsets, table column metadata and column
decode, dictionary keys, values and entries, q datetime and time conversion,
GUID/byte/char payload copies, and Arrow validity bitmaps.

Arrow bitmaps keep polars' word-at-a-time packing; only their buffer allocation
changed, measured at parity (mean ratio 1.004 over five rounds against
`Bitmap::from_trusted_len_iter`).

## Behaviour to be aware of

- Error text changed for oversized and malformed frames. Code matching on the
  string `"safety limit"` will no longer match; the messages now name the
  offending value and the bound it failed.
- A compressed frame whose declared decompressed size is unreachable from its
  payload now fails as a deserialization error and closes the connection, in
  line with every other malformed-frame path.
- A q binary table file whose reported size is zero but which holds content is
  now read completely instead of being rejected.

## Performance

No regression. Measured against kola on 100,000-row fixtures, 50 iterations,
comparing within each run to cancel machine drift: `read wide` 43.3 ms versus
96.3 ms, `read trade` 12.4 ms versus 15.7 ms, `read depth` 14.3 ms versus
17.1 ms, `send trade` 17.9 ms versus 22.4 ms. The scalar round trip remains a
tie.
